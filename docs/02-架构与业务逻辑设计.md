# 02 架构与业务逻辑设计

## 1. 总体架构

框架采用**分层 + 接口抽象**架构，自上而下：

```
┌─────────────────────────────────────────────────────────────┐
│                       前端（Web 监控面板）                     │
│        web/index.html + app.js + style.css（go:embed）        │
└───────────────────────────────┬─────────────────────────────┘
                                │ HTTP /api/*  JSON
┌───────────────────────────────▼─────────────────────────────┐
│                    pkg/monitor（指标与管理 API）               │
│          metrics 注册表 · /api/services · /api/metrics ·      │
│          /api/pools · /api/alerts · /api/config · /api/healthz│
└───────────────────────────────┬─────────────────────────────┘
┌───────────────────────────────▼─────────────────────────────┐
│  internal/invoke（客户端调用链）        internal/server（服务端核心）│
│  filter 链 · 超时 · 重试 · 选择器      服务表 · 请求分发 · 反射调用 │
└───────┬───────────────────────────┬─────────────────────────┘
        │                           │
┌───────▼───────────────────────────▼─────────────────────────┐
│  internal/transport（TCP 传输层）                             │
│  server 监听/accept · conn 读写封装 · 帧收发                   │
└───────┬─────────────────────────────────────────────────────┘
        │
┌───────▼─────────────────────────────────────────────────────┐
│  internal/protocol（帧协议） + internal/codec（序列化）        │
│  message 结构 · encode/decode · JSON/Gob/Binary Codec        │
└───────┬─────────────────────────────────────────────────────┘
┌───────▼─────────────────────────────────────────────────────┐
│  internal/pool（连接池）    internal/registry（注册中心）       │
│  Get/Put · 空闲回收 · 心跳    static 内存实现 · Consul 集成     │
│                             internal/discovery（发现+选择器）   │
└─────────────────────────────────────────────────────────────┘
```

依赖方向：上层依赖下层的**接口**，下层不反向依赖上层；`pool`、`registry`、`discovery` 互不依赖（`discovery` 依赖 `registry` 接口）。

## 2. 服务端启动流程

```
main
 ├─ 解析命令行参数（监听地址、注册中心类型、服务名、TTL、权重）
 ├─ 创建 server.NewServer(配置)
 ├─ server.Register(实现体, 选项)   → 反射提取 ServiceDesc/MethodDesc，登记服务表
 ├─ 启动监听 server.ListenAndServe()
 │    ├─ net.Listen("tcp", addr)
 │    ├─ accept 循环：每连接起 goroutine 处理
 │    ├─ 注册中心注册：registry.Register(实例, TTL)
 │    └─ 心跳 goroutine：每 TTL/2 续约一次，失败计数超限则重新注册
 ├─ 启动健康检查 HTTP 端点（/api/healthz，供 Consul 探测）
 └─ 阻塞等待信号
      └─ 收到 SIGINT/SIGTERM → 优雅关闭：
          停止 accept → 等待在途请求（上限 5s）→ 注销注册 → 关闭连接与监听
```

**连接处理子流程（每连接 goroutine）**：

```
读帧头 → 校验 magic/version → 按 msgType 分发：
  ├─ ping    → 回 pong（连接保活）
  └─ request → 解 header（service/method/traceId/timeoutMs）
               ├─ 查服务表（miss → 返回 StatusNotFound）
               ├─ 执行服务端过滤器链 Before（限流、鉴权占位、日志）
               ├─ 按方法 codec 解码 body → 反射调用 handler
               │    ├─ 调用带独立 context（timeoutMs 截止）
               │    └─ panic 恢复：转为 StatusServerError 响应
               ├─ 过滤器链 After（指标采集）
               └─ 编码响应写回（含 status 与错误信息）
```

## 3. 客户端调用流程（核心时序）

```
调用方
 │  invoke.Client.Call(ctx, service, method, args, reply, opts)
 ▼
 1. 过滤器链 Before（注入 TraceID、记录开始时间）
 2. 从 discovery 取实例列表（本地缓存，无则先拉取）
 3. selector.Select(实例列表, key) → 目标实例
 4. 计算整体 deadline：ctx 与 opts.Timeout 取更早者
 5. 循环（attempt = 0..MaxRetry）：
    ├─ 剩余时间不足 → 返回 ErrDeadlineExceeded
    ├─ pool.Get(ctx) 借连接（带超时；失败 → 可重试错误）
    ├─ 编码请求（codec 按方法配置）→ conn.Send(帧)
    ├─ conn.Recv 等待响应（受单次超时控制）
    ├─ pool.Put(conn) 归还
    ├─ 响应 status == OK        → 解码 reply，成功返回
    ├─ status 为业务错误        → 非重试，立即返回错误
    ├─ 网络/超时/服务端 5xx 类   → 可重试错误：
    │     └─ 方法非幂等且请求可能已送达 → 不重试，返回
    │     └─ 否则退避 delay = base*2^(attempt)*(1+jitter)，等待后继续循环
    └─ 重试计数 +1（上报指标）
 6. 过滤器链 After（记录延迟/结果，采指标）
 ```

**关键不变式**：
- 每次重试都可能选到**不同实例**（重选 selector），实现故障转移；
- 重试只发生在"请求未送达"或"服务端未处理"类错误上；
- 整体 deadline 是硬约束，重试不会突破它。

## 4. 连接池业务逻辑

```
池状态：空闲队列 idleQueue（LIFO） + 活跃数 active + 容量 max

Get(ctx):
  1. 尝试取空闲连接：校验连接活性（读非阻塞探测 / 最后使用时间）
     ├─ 活性 OK → 返回
     └─ 活性失效 → 关闭并继续取
  2. 空闲不足且 active < max → 新建连接（带拨号超时），active++，返回
  3. 已满 → 阻塞等待（select ctx.Done / 空闲归还信号）
     ├─ 等来归还的连接 → 校验后返回
     └─ ctx 超时 → 返回 ErrPoolTimeout

Put(conn):
  1. 连接已过期（idleTimeout）或对端已关闭 → 关闭，active--
  2. 否则 push 回空闲队列，唤醒一个等待者
  3. 空闲数量超过 maxIdle → 关闭最老的空闲连接

后台任务（每池一个 goroutine，可关闭）：
  ├─ 每 5s：扫描空闲连接，最后活跃时间超过 idleTimeout 的关闭剔除
  └─ 每 10s：对空闲连接发 ping，超时未回 pong 的关闭剔除（健康检查）
```

## 5. 服务发现与注册中心业务逻辑

```
注册（服务端侧）：
  Registry.Register(serviceName, 实例{addr, weight, meta, ttl})
    ├─ static：写内存 map，触发 watch 通知
    └─ consul：consul.Agent().ServiceRegister（含 TTL check）
  Heartbeat：每 ttl/2 调用
    ├─ static：更新 LastHeartbeat 时间戳并恢复健康状态
    └─ consul：consul.Agent().PassTTL
  static 管理：可更新实例权重或健康状态；Discover 前按 TTL 核对健康状态，状态变化触发 watch 通知
  Deregister：删除实例，触发 watch 通知

发现（客户端侧）：
  Discovery.Start(serviceNames):
    ├─ 全量 Discover 填充本地缓存
    └─ 启动 watch goroutine：
          static → 订阅变更 channel，更新缓存
          consul → 每 5s 轮询健康实例，版本变化则更新缓存
    └─ 缓存条目：实例 + 失活标记（心跳超时 TTL*2.5 未更新的实例标记失活，
       不参与选择，但保留在列表中供前端展示）
```

## 6. 超时与重试边界（决策表）

| 错误来源 | 错误类型 | 是否重试 | 说明 |
| -------- | -------- | :------: | ---- |
| 拨号失败 / 连接被拒 | retryable | ✅ | 选下一个实例 |
| 借连接超时（池满） | retryable | ✅ | 退避后重试 |
| 发送中断 / 读取超时 | retryable（送达状态不明） | ✅ 仅幂等方法 | 否则可能重复执行 |
| 服务端返回 StatusTimeout | retryable | ✅ | 服务端处理超时 |
| 服务端返回 StatusServerError | retryable | ✅ | 内部错误可换实例 |
| 服务端返回 StatusNotFound | non-retryable | ❌ | 服务/方法不存在，重试无意义 |
| 服务端返回 StatusClientError | non-retryable | ❌ | 参数错误，重试必失败 |
| 业务响应错误码非零 | non-retryable | ❌ | 业务已执行，禁止重试 |

## 7. 优雅关闭时序

```
客户端                        服务端
  │  SIGTERM                    │ SIGTERM
  │ ──────────────────────────▶ │
  │                             │ 1. 停止 accept，关闭监听
  │                             │ 2. 等待在途请求处理完成（≤5s）
  │                             │ 3. registry.Deregister（实例下线）
  │                             │ 4. 关闭全部连接、池、心跳 goroutine
  │  watch 收到下线通知          │
  │  本地缓存剔除该实例          │
  │  （此后新请求不再选到它）     │
  │  关闭连接池/采样器           │
```

## 8. 数据模型（跨层流转）

```
Invocation{ TraceID, Service, Method, Args, TimeoutMs, Metadata }
   │ codec.Encode  → Body []byte
   ▼
Frame{ Magic, Version, MsgType, Flags, CodecID, Status, ReqID, HeaderLen, BodyLen, Header, Body }
   │ protocol.Encode → 23 字节定长头 + Header + Body
   ▼
TCP 字节流（transport 层收发）
   ▼
服务端 protocol.Decode → Frame → 按 ReqID 关联响应（客户端侧按 ReqID 匹配等待者）
```

各环节详情见 [04-协议与接口定义](04-协议与接口定义.md)。

## 9. 并发模型总结

| 组件 | 并发模型 |
| ---- | -------- |
| 服务端 accept | 单 goroutine accept，每连接一个读写 goroutine，每请求一个执行 goroutine（带 timeout context） |
| 客户端调用 | 每次 Call 独立 goroutine；等待响应通过 ReqID → channel 映射匹配 |
| 连接池 | 每地址一池，池内 mutex + channel 条件等待 |
| 注册中心 | static 用 RWMutex；watch 用 channel 广播 |
| 指标 | 原子计数器 + 采样窗口（带锁的环形桶） |
| 前端 | 浏览器轮询 JSON API（无 WebSocket，保持简单） |
