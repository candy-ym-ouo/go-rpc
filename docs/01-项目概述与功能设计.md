# 01 项目概述与功能设计

## 1. 项目背景与目标

### 1.1 背景

微服务架构下，服务间通信是最基础的设施。生产级 RPC 框架（如 gRPC、Dubbo）功能完备但实现复杂、依赖重，难以看清"一次 RPC 调用到底发生了什么"。本项目用 Go 从零实现一个**教学与工程实践并重**的轻量级 RPC 框架，把一条完整调用链上的每个环节（定义、发现、序列化、传输、池化、超时、重试、监控）都以清晰、可读、可扩展的代码呈现出来。

### 1.2 目标

1. 实现题目要求的五大能力：**接口定义、序列化协议、连接池、超时重试、服务发现集成**；
2. 提供简单直观的 **Web 监控前端**，让框架行为"看得见"；
3. 代码结构清晰、可扩展，规模可控：**Go 代码（不含测试）2000~2200 行、20~25 个文件**；
4. 全部核心逻辑基于 Go 标准库，仅 Consul 集成引入官方客户端。

### 1.3 非目标

- 不做跨语言支持（仅 Go ↔ Go）；
- 不做 TLS/双向认证（预留 flags 扩展位）；
- 不做流式调用（仅请求-响应模式）；
- 不做完整 protobuf IDL 编译链（预留扩展点，见 5.5）。

## 2. 核心功能设计（扩写）

### 2.1 接口定义（Interface Definition）

**业务诉求**：使用者只需定义一个 Go interface，框架即可自动完成服务注册、方法寻址、参数序列化与结果反序列化，无需手写任何网络层代码。

**设计要点**：

1. **服务描述模型**：框架内部用 `ServiceDesc` 描述一个服务、`MethodDesc` 描述一个方法，包含：
   - 服务名（默认取接口类型名，如 `HelloService`，可被 tag 覆盖）；
   - 方法名、方法签名的输入/输出类型（通过反射提取）；
   - 每个方法可独立配置的元数据：序列化类型、超时时间、最大重试次数、幂等标记；
   - 方法索引表（名字 → 方法），用于请求分发 O(1) 寻址。
2. **注册方式**：`server.Register(impl any, opts ...RegisterOption)`，通过反射解析：
   - 校验方法签名必须为 `func(ctx context.Context, req *T) (*R, error)` 形态（其余形态拒绝注册并给出明确错误）；
   - 生成 `MethodDesc` 并登记到服务表；
   - 建立 `handler = reflect.ValueOf(impl)` 的调用闭包，后续请求分发时直接执行。
3. **方法级配置**：支持通过结构体方法上的 tag（如 `` `rpc:"timeout=2s,retry=2,idempotent,codec=json"` ``）声明策略，运行时按方法读取，未声明则回退到全局默认配置。
4. **服务注销**：`server.Deregister(serviceName)`，供优雅关闭与热更新使用。

### 2.2 序列化协议（Serialization Protocol）

**业务诉求**：请求参数与响应结果在网络上传输前必须编码为字节流；不同场景（调试、性能、兼容）需要不同协议，且协议应可插拔。

**设计要点**：

1. **Codec 抽象**：统一的 `Codec` 接口（`Encode/Decode/Name`），框架内部只面向接口编程，新增协议零侵入。
2. **内置三种实现**：
   - `json`：基于 `encoding/json`，可读性好，适合调试与跨语言；
   - `gob`：Go 原生二进制，类型信息内嵌，适合 Go ↔ Go 默认场景；
   - `binary`：自定义紧凑二进制编码器（手写反射编解码，支持基本类型、嵌套 struct、slice/map），体积最小、速度最快，作为性能优先场景的默认选项。
3. **协议选择规则**：优先级为 方法 tag > 服务级配置 > 客户端调用参数 > 全局默认（`gob`）。
4. **扩展点**：外部可注册自定义 Codec 到全局 Codec 注册表（`codec.Register(custom)`），并通过帧头 codec 字段（0/1/2 预留 3~15）寻址。

### 2.3 连接池（Connection Pool）

**业务诉求**：每次 RPC 调用都新建 TCP 连接会引入巨大的握手开销；连接池复用连接，降低延迟与资源占用，并承担健康检查职责。

**设计要点**：

1. **池结构**：按**目标实例地址分池**（`map[addr]*ConnPool`），每池包含：
   - 空闲连接队列（带容量的 channel 或 slice + mutex）；
   - 活跃连接计数、总容量上限（max）、最小保持数（min）；
   - 空闲超时（idleTimeout）：超过该时间未使用的空闲连接被关闭回收；
   - 获取等待队列：池满且未超时时，获取方阻塞等待（可被 context 取消）。
2. **借还语义**：
   - `Get(ctx)`：优先取空闲连接 → 检查连接健康（最后活跃时间/是否被服务端关闭）→ 不健康则丢弃重取 → 空闲不足且未达 max 则新建 → 达 max 则等待；
   - `Put(conn)`：归还时校验连接是否可复用（未超时、未被对端关闭），可复用则回空闲队列，否则关闭；归还过程非阻塞。
3. **健康检查与心跳**：
   - 后台定时任务对池内空闲连接发送协议层 `ping`（帧 msgType=2），超时未收到 `pong` 的连接立即关闭剔除；
   - 新建连接建立时执行一次握手（可配置），失败则快速失败返回错误。
4. **统计**：`Stats()` 返回活跃数、空闲数、总容量、等待数、创建/关闭累计数，供监控前端展示。

### 2.4 超时重试（Timeout & Retry）

**业务诉求**：网络抖动、服务重启、慢节点在分布式环境中是常态。框架必须保证调用"有界"（不会无限挂起），并在可安全重试的失败场景下自动恢复。

**设计要点**：

1. **两级超时**：
   - **单次尝试超时**：一次请求从发送到收到响应的最长时间（默认 2s），由帧头 `timeoutMs` 字段传给服务端，服务端据此约束 handler 执行；
   - **整体截止时间**：一次调用（含所有重试）的总 deadline，由客户端 context 驱动；每次重试前计算剩余时间，剩余不足则直接放弃并返回 `ErrDeadlineExceeded`。
2. **重试策略**：
   - 配置项：最大重试次数（默认 2）、退避基数（默认 200ms）、抖动系数（默认 0.3）；
   - 退避公式：`delay = base * 2^(attempt-1) * (1 + random(0, jitter))`，防止重试风暴；
   - 重试触发条件：仅对**可重试错误**重试 —— 连接错误、读取超时、服务端返回 `StatusServerError`/`StatusTimeout`/`StatusUnavailable`；业务错误（`StatusClientError`、业务码非零）一律不重试；
   - **幂等保护**：仅当方法标记 `idempotent`（tag 或注册时指定）或错误发生在"请求尚未送达/送达状态不明"时才重试；明确收到业务错误响应绝不重试。
3. **错误归类**：传输层/协议层错误在客户端被分类为 `retryable` 或 `non-retryable`，重试逻辑只消费分类结果，保持职责单一。
4. **重试计数上报**：每次重试累加到监控指标（`retry_total`），前端可见。

### 2.5 服务发现集成（Service Discovery）

**业务诉求**：服务实例地址不写死，由注册中心统一管理；实例上下线时客户端自动感知并调整流量，避免连到已下线节点。

**设计要点**：

1. **注册中心抽象**：`Registry` 接口统一四种能力：
   - `Register`：注册实例（服务名、地址、权重、元数据、TTL）；
   - `Deregister`：注销实例；
   - `Heartbeat`：续约（TTL 租约模式）；
   - `Discover` / `Watch`：拉取实例列表 / 订阅变更。
2. **静态注册中心（static）**：内存实现，`map[serviceName][]Instance + RWMutex`，提供注册/注销/查询，并支持模拟上下线（供演示与测试）。作为默认注册中心，保证框架开箱即用、零外部依赖。
3. **Consul 集成**：通过 `hashicorp/consul/api` 官方客户端：
   - 服务注册到 Consul catalog，附带 HTTP 健康检查端点（`/api/healthz`）；
   - 心跳续约：注册 TTL 检查，客户端 goroutine 周期性 `PassTTL` 续约，续约连续失败 N 次后尝试重新注册；
   - 服务发现：`Discover` 使用 Consul catalog 健康服务查询；`Watch` 基于轮询+版本比对（Consul blocking query 语义简化版），变更推送到本地缓存。
4. **客户端发现层**：`Discovery` 维护本地实例缓存（服务名 → 实例列表），启动时全量拉取，之后靠 Watch 增量更新；同时提供"手动刷新"兜底。
5. **负载均衡**：`Selector` 从实例列表中选一个目标，内置四种策略（随机/轮询/加权/一致性哈希），见 3.2。

## 3. 扩展功能设计

### 3.1 过滤器链（Filter / 中间件）

- 客户端过滤器：`Before`（编码前，注入 TraceID、记录开始时间、校验参数）与 `After`（响应后，记录延迟/错误、采指标）；
- 服务端过滤器：`Before`（鉴权占位、限流判断、日志）与 `After`（panic 恢复、指标采集）；
- 内置过滤器：**日志**（打印调用摘要）、**指标**（调用监控的数据来源）、**TraceID**（为每次调用生成/透传 trace id，日志与前端可关联）；
- 过滤器以链式顺序执行，支持自定义注册，用于扩展业务无关横切逻辑。

### 3.2 负载均衡（Load Balance）

`Selector` 接口 + 四种实现：

| 策略 | 行为 | 适用场景 |
| ---- | ---- | ---- |
| 随机 | 从健康实例中随机选一个 | 默认，均衡性好 |
| 轮询 | 原子计数器取模 | 实例权重相同 |
| 加权轮询 | 按实例 weight 分配概率 | 异构节点 |
| 一致性哈希 | 按调用 key（如方法名+参数摘要）哈希到实例，最小化迁移 | 有状态场景（会话亲和） |

选择器只作用于**健康实例**（发现层已剔除失活实例），实现位于 `internal/discovery/selector.go` 单文件。

### 3.3 监控与指标（Metrics）

- 计数：请求总数、成功数、失败数、重试次数、超时数、连接创建/关闭数；
- 时延：滑动窗口（最近 60 秒）内平均延迟与 P99（分桶直方图简化实现）；
- QPS：每秒请求数的滑动窗口统计；
- 连接池状态：每目标地址的活跃/空闲/等待数；
- 数据源：客户端与服务端共享 `pkg/monitor` 中的指标注册表，通过 `metrics.Get()` 导出为 JSON。

### 3.4 优雅关闭（Graceful Shutdown）

1. **服务端**：收到 SIGINT/SIGTERM → 停止 Accept 新连接 → 等待处理中请求完成（带整体超时上限）→ 从注册中心注销 → 关闭监听与连接池；
2. **客户端**：关闭时停止心跳与 watch goroutine、关闭连接池、释放指标采样器。

### 3.5 管理前端（简单 Web UI）

- 内置 HTTP 服务（默认 `:8080`）提供：
  - JSON API（`/api/services`、`/api/metrics`、`/api/pools`、`/api/config`、`/api/healthz`）；
  - 静态前端页面（`web/index.html` + `app.js` + `style.css`，通过 `go:embed` 嵌入二进制，无需外部静态服务器）。
- 前端为单页三面板布局，5 秒轮询刷新，展示服务发现、调用监控、连接池状态，详见 [05-前端界面设计](05-前端界面设计.md)。

## 4. 非功能需求

| 维度 | 要求 |
| ---- | ---- |
| 并发 | 服务端每连接一 goroutine + 每请求处理池化（简单实现：goroutine per request，默认 GOMAXPROCS 感知）；客户端连接池并发安全 |
| 健壮性 | 服务端 handler panic 必须捕获并转为错误响应，不得击穿进程；解码失败返回协议错误 |
| 可观测性 | 日志统一输出（时间、级别、调用信息、traceId），指标可供前端展示 |
| 可扩展性 | Codec / Registry / Selector / Filter 均为接口 + 注册表模式，新增实现不改核心代码 |
| 可测试性 | 核心组件（协议、连接池、重试、选择器、静态注册中心）均可独立单测，不依赖真实网络 |
| 规模约束 | Go 源码（不含 `*_test.go`）行数 2000~2200、文件数 20~25，见 [03-模块与文件规模规划](03-模块与文件规模规划.md) |

## 5. 技术选型

| 类别 | 选择 | 理由 |
| ---- | ---- | ---- |
| 语言/版本 | Go 1.21+ | 标准库覆盖网络、反射、编码，无需外部框架 |
| 传输层 | TCP（`net` 包） | 可控、教学清晰；帧协议自研 |
| 序列化 | `encoding/json`、`encoding/gob`、自研二进制 | 覆盖可读/默认/高性能三档 |
| 注册中心 | 内置静态实现 + `hashicorp/consul/api` | 默认零依赖，可选 Consul 集成 |
| 前端 | 原生 HTML/CSS/JS + `go:embed` | "简单前端"要求，无构建工具链 |
| 依赖清单 | 仅 `hashicorp/consul/api`（可选构建标签隔离） | 保持依赖极简 |

> 依赖隔离策略：Consul 相关代码位于独立包并建议以 `//go:build consul` 构建标签隔离，保证默认 `go build` 无外部依赖。
